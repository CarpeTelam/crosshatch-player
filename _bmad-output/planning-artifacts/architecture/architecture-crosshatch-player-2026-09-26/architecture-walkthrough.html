Stop 1What the engine is for

AD-23

crosshatch turns the e-reader into a console for simple, turn-based games, in the spirit of CrossPlay's catalog. A game is a Lua script in a .cpgame file. You install it by dropping the file on the SD card; the firmware never changes.

In scope

Pen-and-paper, board, card, dice and word games, puzzles, and parlor games: tic-tac-toe, Dots and Boxes, Battleship, Hangman, Sudoku, a party guessing game with a countdown.

Out of scope

Platformers, action and physics games, anything animation-driven. There is no frame loop, no sprites, no scrolling, no drag input, no sound, and no timer faster than one second.

This scope is a binding rule, not a v1 shortcut. Every later API addition has to serve a game in scope, and performance is stated per move ("a move answers within about a second"), never as frames per second. The e-ink panel takes most of a second per update, so the whole design leans into that instead of fighting it.

Stop 2The layers and who may depend on whom

AD-1AD-2AD-4

The engine is a hexagonal design. lib/GameCore holds everything about sessions, seats, turns, snapshots and the radio protocol. It has no device dependencies, so it is tested on a laptop against a fake radio that drops and reorders packets. Everything that touches Lua, the radio, the SD card or the screen is an adapter around it.

All of this is fork-only code behind a single build flag, FREEINK_CAP_GAMES, set for the X4 Pro and Sticky builds only. The ESP32-C3 builds carry none of it, but the libraries must still compile there.

Stop 3A game is five functions

AD-8AD-9AD-11

main.lua returns a table with setup, status, apply, draw and input. The trick that makes one script work alone, in pass-and-play and across two devices is where each function runs.

  • state is the whole game, and only apply changes it. Every apply starts from a fresh decode of the snapshot, so changes a script makes inside draw or input simply vanish.
  • ui is per screen. Cursors and selections live in a separate table that is never sent or saved, one per local seat, so pass-and-play never leaks one player's selection to the other.
  • The script decides turn order through status, which must be a pure function of state; the runtime enforces it and ships the host's answer to the guest.
  • Seats are fixed before setup. Solo is one seat. In Play Nearby the host is seat 1, and a remote move's seat comes from which device sent it, never from the move itself.

Stop 4From file to launcher

AD-15AD-16AD-22

There is one way in for v1: the SD-card inbox. A web Games page is deferred, which keeps the web server untouched.

A package holds only flat, whitelisted files: manifest.json, main.lua, extra modules, and PNGs. Lua must be source text; precompiled bytecode is refused because PUC Lua doesn't verify it. Each package gets an 8-byte content hash that pack_game.py computes the same way, and two devices only match in Play Nearby when the hashes agree.

The restaurant test: from Home, a solo or pass-and-play game starts in at most three taps (Games, the game, a mode), and nothing in v1 asks for typing.

Stop 5Inside a match: tasks and locks

AD-5AD-18AD-20

Two review rounds found that most of the ways this could go wrong were about threads: a deadlock on the render lock during teardown, a hung script, a pushed screen starving the radio. The fix is strict ownership. One GameMatchActivity owns the whole match, and each task has one job.

  • Stopping a script is cooperative: the match sets a cancel flag that the instruction hook turns into a Lua error. If the script is stuck inside a C library call for 500 ms, the match throws the VM away and frees its memory arena in one call.
  • Leaving runs in a fixed order: tell the other device, flush the link, stop the VM, turn the radio off. Back and Home open a pause menu instead of quitting.

Stop 6A Play Nearby turn

AD-10AD-13

The link and the session each own their own counter. The link numbers frames for acknowledgement; the session numbers states with ver, which only ever goes up, even across a rematch.

A state is encoded with one canonical codec whose bytes are written down, so a Python reference encoder produces identical output for test vectors. The state must fit in 1,400 bytes in every mode, including solo, so a game hits the limit in pass-and-play long before it breaks a two-device match. Resend every 400 ms and drop after 10 s are provisional until the radio work measures real devices.

Stop 7Passing the device without leaking secrets

AD-12AD-21

E-ink ghosting leaves a faint copy of the last screen behind, which would show one player's ships to the next. So in pass-and-play with hidden = true, the runtime owns the hand-off and scripts cannot skip it.

The full match lifecycle adds a pause menu (Back or Home), an end-of-round menu with Play again and Leave, and error and "player left" views. They are all views inside the one match activity, never separate screens, so nothing can stop the radio link by covering it.

Stop 8Drawing, and a shared look

AD-7AD-24

Scripts never touch the framebuffer. Every ch.gfx call appends to a display list of at most 2,048 commands; when draw returns, the frame is swapped to the render task, which paints it. The script asks for a fast, half or full refresh, and the runtime may only strengthen that. Fills can use four grays as dot patterns; lines, text, icons and images are black or white.

Games share a curated icon library, and so do the launcher and the runtime's own screens, so crosshatch games look like they belong together. Icon names are part of the API: a later level can add names but never rename or repurpose one.

A game that needs something the library doesn't have ships its own PNGs, converted to black and white at install and drawn with ch.gfx.image.

Stop 9The guardrails

AD-6AD-10AD-14AD-23

Each game runs in a sandbox with fixed budgets. Breaking one ends the round with a short error view and a single Back button; in Play Nearby the other device is told the match ended.

BudgetLimitWhy this size
Lua memory per game256 KBOne PSRAM arena; the spike's tic-tac-toe peaked near 26 KB.
Instructions per call2,000,000About one second on the S3, so a tap always answers.
Game state1,400 BFits one ESP-NOW v2 frame with room for headers.
One move256 BMoves describe what a player did, not the board.
ch.store data4 KBHigh scores and settings, per game, per device.
Drawing calls per frame2,048Bounds the display list at 32 KB.
Shortest timer1,000 msCountdowns for parlor games, nothing faster.
Package size256 KBAt most 32 flat files, each ≤ 128 KB unpacked.

Scripts get table, string, math and utf8, and nothing that reaches files, the OS or the debugger. All host functions live under one global table, ch, versioned by an API level that only grows.

Stop 10Staying mergeable with upstream

AD-2AD-3

Upstream merge pain is what started this project, so the upstream files v1 may touch are listed by name. A fork-only CI job fails any PR that changes an upstream file off this list; one spare slot exists, and anything more needs an architecture update first.

Upstream fileChange
platformio.iniThe build flag for the six X4 Pro and Sticky envs; one cppcheck suppression for vendored Lua.
english.yamlSTR_GAMES_* strings, appended.
test/CMakeLists.txtTwo host test suites.
ActivityManager.h, .cppThe Games menu item and goToGames().
HomeActivity.h, .cppThe Games entry on Home, reusing an existing list icon.
CoverGridHomeUi.h, .cppThe Games tile, drawn from the icon library.

That's nine files, each change guarded where the language allows. Vendored Lua is shielded from the formatter by its own .clang-format file instead of an edit to the upstream format script.

Stop 11Still open

No blockers remain, but a few numbers wait on measurements before they're tuned:

  • Once a second device arrives: ESP-NOW reliability between two devices, the battery cost of a match, and how the Sticky and a mixed X4 Pro and Sticky pair behave. Until then the link code is built and tested against the simulated link, and nothing else waits on it.
  • On one device: whether memory recovers after the radio shuts down.

Lua 5.5.1 is taken to run at least as well as the 5.4 the spike measured, so no re-run gates the API. A problem found during implementation is fixed then, with 5.4.9 as the fallback.

Deliberately left for later: a web Games page, partial-screen refresh, more than two players, reconnecting after a drop, and the game starter repo.
