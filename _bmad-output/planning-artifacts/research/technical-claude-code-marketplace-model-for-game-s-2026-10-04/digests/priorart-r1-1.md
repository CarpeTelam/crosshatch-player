# Digest: priorart r1

Dimension D3: prior art for decentralized package catalogs consumed by constrained or non-git clients. All claims come from sources fetched this run (2026-10-04). Several fetches went through a summarizing fetch tool, so the wording in quotes is the tool's extraction of the page, not a byte-exact copy. Confidence is set to reflect that.

## Findings

### F-Droid (signed index, third-party repos by URL + fingerprint)

- claim: F-Droid publishes index v1 as a "signed JAR file that contains index-v1.json". Clients are told: "The best method is to verify the JAR signature, then extract index-v1.json if it validates." Detached GPG `.asc` signatures are also published for the JSON files. | source: https://f-droid.org/docs/All_our_APIs/ | F-Droid | undated page | accessed 2026-10-04 | confidence high | class pattern
- claim: Index v2 adds a small signed entry point (`entry.jar`, `entry.json`, `entry.json.asc`) "which is signed by a JAR and a GPG signature and lists the available index and diff files". Index v2 also supports "diff" files that contain only the changes. | source: https://f-droid.org/docs/All_our_APIs/ | F-Droid | undated | accessed 2026-10-04 | confidence high | pattern
- claim: The live `entry.json` has this shape: `{timestamp (ms), version: 30000, maxAge: 14, index: {name:"/index-v2.json", sha256, size, numPackages}, diffs: {"<fromTimestamp>": {name:"/diff/<ts>.json", sha256, size, numPackages}, ...}}`. The signed entry therefore pins the sha256 and size of the full index and of every diff. The client picks the diff keyed by the timestamp it already holds, and falls back to the full index when no such diff exists. | source: https://f-droid.org/repo/entry.json | F-Droid (live file) | timestamp 1791060793421 | accessed 2026-10-04 | confidence high (structure); med (the client-selection logic is inferred from the keys, not from a spec) | pattern
- claim: Scale data point: the main repo's full index-v2.json is 62,626,210 bytes for 4,525 packages, and the diffs run about 4.6–5.3 MB each. The full index is far too large for a microcontroller to parse in RAM, so a device client needs a small entry/summary layer and either streaming parsing or per-package files. | source: https://f-droid.org/repo/entry.json | F-Droid | live | accessed 2026-10-04 | confidence high | pattern
- claim: In index-v2, each package version carries `file: {name, sha256, size}` plus `manifest: {versionName, versionCode (integer), usesSdk: {minSdkVersion, targetSdkVersion}, signer: {sha256: [...]}}`. Compatibility gating is done with integer minSdk/targetSdk fields, which is the direct analog of the device's "integer API level". The repo object lists `mirrors: [{isPrimary, url}, ...]` (onion mirrors included) next to `address` and `timestamp`. | source: https://gitlab.com/fdroid/fdroidserver/-/raw/master/tests/repo/index-v2.json | fdroidserver (test fixture) | fixture timestamp 1676634233000 | accessed 2026-10-04 | confidence high | pattern
- claim: F-Droid also publishes `signer-index.json`, a "Simple index file that lists the SHA-256 fingerprint of each signer used by f-droid.org to sign each package". Package signer identity is published separately from the file hash. | source: https://f-droid.org/docs/All_our_APIs/ | F-Droid | undated | accessed 2026-10-04 | confidence high | feature
- claim: Users add third-party repos by URL plus signing-key fingerprint, which can be carried in one string such as `https://host/fdroid/repo/?fingerprint=<SHA-256 hex>`. When that string is pasted into Add Repo, the client splits out the fingerprint. Without a fingerprint the model is trust-on-first-use. | source: https://gitlab.com/fdroid/fdroidclient/issues/50 ; https://newpipe.net/blog/announcement/f-droid/pinned/f-droid-repo/ (via search summary) | F-Droid GitLab / NewPipe | various | accessed 2026-10-04 | confidence med (from search-result summaries, not the full pages) | pattern
- claim: Documented failure: when a repo was added by hand with the `?fingerprint=` query left in the stored URL, the error did not show at add time. It showed "later on when you try to install an APK" as "repo failed to verify". The issue (#2078) is a duplicate of #1787, so the problem recurred. Lesson: normalize the source URL and verify the key when a source is added, so a bad source fails then and not at install. | source: https://gitlab.com/fdroid/fdroidclient/-/issues/2078 | F-Droid GitLab | affects ≤1.9 per report | accessed 2026-10-04 | confidence med | pattern (lesson)

### Flipper Zero app catalog (closest microcontroller analog)

- claim: Developers submit by PR. They fork flipper-application-catalog, branch as `<username>/<appid>_<appversion>`, and add `applications/<category>/<application-id>/manifest.yml`. After approval, which usually takes 1–2 business days, the app is in the catalog "in a few minutes". | source: https://github.com/flipperdevices/flipper-application-catalog/blob/main/documentation/Contributing.md | Flipper Devices | main branch | accessed 2026-10-04 | confidence high | pattern
- claim: The manifest pins source rather than binaries: `sourcecode: {type: git, location: {origin, commit_sha, subdir?}}`. The catalog builds the package itself ("bundler script to build the app package", uploaded to "Flipper Application Archivarius"). Other fields are `id` ("lowercase string with no spaces. Must be globally unique"), `category` (a fixed set of 11), `version` as `major.minor`, descriptions, a changelog with `@file` inclusion, at least one screenshot, and optional `targets`. | source: https://github.com/flipperdevices/flipper-application-catalog/blob/main/documentation/Manifest.md | Flipper Devices | main | accessed 2026-10-04 | confidence high | pattern
- claim: The version must increase: "All submitted app updates must use a higher version number than the previous version, otherwise the update will be rejected." Monotonic versions are enforced at the catalog, which gives clients a simple way to detect updates. | source: same Manifest.md | Flipper Devices | main | accessed 2026-10-04 | confidence high | pattern
- claim: Apps must be "buildable with uFBT and compatible with the latest Release or Release Candidate firmware version." | source: Contributing.md (above) | Flipper Devices | main | accessed 2026-10-04 | confidence high | pattern
- claim: FAP API gating: "Apps are built for a specific API version". "The App Loader checks if the app's major API version matches the firmware's major API version." API versions are semver: major on breaking changes (removed function or variable, changed signature), minor on additions. A firmware-exported symbol table resolves imports at load time, and the build tool warns on missing symbols. | source: https://raw.githubusercontent.com/flipperdevices/flipperzero-firmware/dev/documentation/AppsOnSDCard.md | Flipper Devices | dev branch | accessed 2026-10-04 | confidence high (major-match rule); low (the minor rule was not stated in the fetched text) | pattern
- claim: The catalog keeps one build per (app version × SDK API version × target). An app page lists rows such as "1.3.5 / 88.2 f7", "87.1 f7" and "86.0 f7", each with "Build succeeded", a download count and "get build" / "get logs" API links. The server rebuilds from the pinned source for each new SDK, and the client fetches the build that matches its firmware's API. | source: https://catalog.flipperzero.one/application/67f379d625a4a6f1fb4a57f7/page | Flipper Devices | live | accessed 2026-10-04 | confidence high (the table); med (that the client selects by API, inferred) | pattern
- claim: The device reports `firmware.api.major` / `firmware.api.minor` in its device info, which a companion app can read to choose a build. Apps are installed via the iOS/Android apps or Flipper Lab (lab.flipper.net). | source: search summary (code.popov.link firmware mirror); https://github.com/flipperdevices/flipper-application-catalog | Flipper / mirror | n/a | accessed 2026-10-04 | confidence med | feature

### Homebrew taps (the git-based analog of a Claude Code marketplace)

- claim: "`brew tap <user>/<repository>` clones `https://github.com/<user>/homebrew-<repository>`". `brew tap <user>/<repository> <URL>` accepts any git URL. Taps update during `brew update` (git pull). | source: https://docs.brew.sh/Taps | Homebrew | current docs | accessed 2026-10-04 | confidence high | pattern
- claim: On name collisions: "A tap may contain a formula with the same name as one in homebrew/core. Use the fully qualified name to select the formula from a particular tap" (`user/repo/formula`). The short name resolves to core. | source: https://docs.brew.sh/Taps | Homebrew | current | accessed 2026-10-04 | confidence high (FQN); med (core precedence is the tool's paraphrase) | pattern
- claim: Trust model: "Code in a tap can run with your user's privileges." Since Homebrew 6.0.0, non-official taps need explicit trust (`brew trust user/repo[/formula]`, `brew untrust`), and "Commands that need to load an untrusted tap or item will fail until the relevant trust is granted". Official taps are always trusted. Installing by fully qualified name reportedly counts as trust for that one install. `HOMEBREW_NO_REQUIRE_TAP_TRUST` is deprecated. | source: https://docs.brew.sh/Tap-Trust | Homebrew | 6.0.0 (release date given by the fetch tool as 2026-06-11, unverified) | accessed 2026-10-04 | confidence med (6.0 version and FQN bypass); low (the date) | version/pattern
- claim: Bottles (prebuilt binaries) are declared in the formula as `bottle do root_url ...; sha256 cellar: ..., arm64_tahoe: "<hex>", sequoia: "<hex>" end`, with one sha256 per platform tag. Homebrew skips a bottle and builds from source when "the bottle is not up to date (e.g. missing or mismatched checksum)", when no compatible tag exists, or when the cellar does not match. Core bottles are hosted on GitHub Packages. The pattern is a git-hosted manifest that pins a per-platform hash, with binaries stored elsewhere. | source: https://docs.brew.sh/Bottles | Homebrew | current | accessed 2026-10-04 | confidence high | pattern

### MicroPython mip (an on-device installer on microcontrollers)

- claim: mip runs on the device and uses the index `https://micropython.org/pi/v2`. Package metadata URL: `"{}/package/{}/{}/{}.json".format(index, mpy_version, package, version)`, so the bytecode ABI version is part of the path and the client is served only builds for its ABI. Files are content-addressed: `"{}/file/{}/{}".format(index, short_hash[:2], short_hash)`. `github:` sources are rewritten to `raw.githubusercontent.com/{org}/{repo}/{branch}/{path}`. Download chunk size is `const(128)` bytes. | source: https://raw.githubusercontent.com/micropython/micropython-lib/master/micropython/mip/mip/__init__.py | MicroPython | master | accessed 2026-10-04 | confidence high | pattern
- claim: The package.json format is `urls: [[dest, src], ...]`, `deps: [[name, version], ...]` (deps may be `github:org/repo`), and `version`. Third parties publish by hosting a package.json in any GitHub or GitLab repo, with no central registration. | source: https://docs.micropython.org/en/latest/reference/packages.html | MicroPython | latest docs | accessed 2026-10-04 | confidence high | pattern
- claim: Integrity gap: mip uses the hash only to skip files that already exist (`_check_exists`). It does not appear to verify a downloaded file against its hash, and the docs do not cover TLS verification. This is a counter-example: a device client should verify the hash after download. | source: mip/__init__.py (above) | MicroPython | master | accessed 2026-10-04 | confidence med (based on the fetch tool's reading of the source, not a line-by-line review) | pattern (lesson)

### TUF (signed-metadata baseline)

- claim: TUF spec v1.0.36 (last modified 2026-08-05) defines the roles root (delegates keys), targets (file hashes and lengths), snapshot (versions of all targets metadata) and timestamp (an online key signs the snapshot hash, frequently). Each role has threshold signatures. It defends against rollback (versions must not decrease), freeze (expiry), mix-and-match (snapshot), endless data (length limits) and arbitrary installation (hash match). Root keys rotate through a chain of root.json versions, each signed by the old and new keys. | source: https://theupdateframework.github.io/specification/latest/ | TUF project | v1.0.36, 2026-08-05 | accessed 2026-10-04 | confidence high | version/pattern
- claim (synthesis, flagged): F-Droid's entry.json, a small signed root that pins the hash and size of a larger index, is a lightweight form of TUF's timestamp→snapshot→targets chain. When a device's TLS skips certificate verification, the transport does not stop an attacker from swapping the catalog, so integrity has to come from hashes pinned in a signed or otherwise trusted root. That root needs a monotonic version or timestamp to block rollback and freeze. | source: inference from the F-Droid and TUF sources above | — | — | accessed 2026-10-04 | confidence med | pattern

- The Homebrew 6.0.0 release notes, to confirm the release date and the FQN trust bypass.
