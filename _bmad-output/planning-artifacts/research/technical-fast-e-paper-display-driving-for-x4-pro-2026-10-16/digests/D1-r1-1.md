## Controller-level vs panel-specific (Q4)
- Controller-level (portable to any SSD1677/UC82xx): overlapped/async refresh with BUSY wait deferred; changed-rectangle window + skip-unchanged frame; differential two-plane update; SPI at controller-rated clock; PLL frame-rate register (UC82xx 0x30; SSD1677 frame rate lives inside the 0x32 LUT bytes); forced temperature.
- Panel-specific: the DU LUT bank itself (Ink-boy reuses the X3 UC8279 bank on an X4 Pro UC8279 0x68 batch), the 40% frame scaling, pll 0x0F, cleaning interval, VCOM tweaks. Ink-boy gates the preset to UC8279 variant 0x68 and keeps stock on SSD1677/UC8179, so nothing in it validates SSD1677 fast driving.

## Leads
- Missing SDK commit ec2857f (the actual fast driver). Not in Free-Ink/freeink-sdk. Try the author's other repos and the "thebitsworld" GitHub user.
- GameBoyActivity.h says "Started from the Ink-boy fork of CrossInk" and the preset comment cites "1.8.1 betas" (CrossInk here is 1.6.1): the fast-screen code was authored in another downstream project and copied back; platformio.ini references a `src/psxe/` PS1 core absent from the tree. That downstream project likely holds the driver.
- Contradiction: README says the custom LUT drives the panel "outside of its normal operating parameters" and "may shorten lifespan"; the code comment says drive levels and voltages stay stock and only frame counts (40%) and PLL change.
- "x4-boy" (Xteink X4, Reddit) is a separate, earlier GB-on-e-ink project.
- Upstream freeink-sdk a3a920d (2026-10-15) "Fix e-ink ghosting ... for eego" and e91e34e VCOM note are current SSD1677 ghosting evidence.
