## Key excerpts

Glider README (Modos-Labs/Glider@ed94ef7):
```
In terms of driving the screen panel, depending on the pixel value (1 or 0), each pixel would be
driven either with a positive voltage or a negative voltage. A global counter can be used to count
the frames elapsed and stop driving the pixels after a predefined period of time (for example,
100ms). Two framebuffers are typically used for determining if the pixel has changed color or not.
If not, then the pixel does not need to be driven.
```

## Leads
- Every per-pixel fast-driving precedent found (Caster/Glider, PaperBoy, epdiy, NekoCal, Inkplate, essentialscrap) drives a bare TFT panel over the parallel source/gate bus; none does it through an SSD/UC controller IC. A controller-based 800x480 SPI panel can only emulate per-pixel budgets by rewriting both RAM planes between short LUT passes.
- SSD1677 datasheet still needed: exact 0x32 byte count, group count, TP/RP fields, frame-rate register, VSH/VSL bytes. Candidates: Good Display spec PDF for GDEQ0426T82; Rust `ssd1677` crate (docs.rs/crate/ssd1677/0.1.0).
- GxEPD2's GDEQ0426T82 class avoids 0x32 entirely and uses the 0x1A temperature-register trick.
- Contradiction: reseller timings for GDEQ0426T82 differ (0.42 s vs 1 s partial; 1.5 s vs 0.76 s fast); measure on hardware.
