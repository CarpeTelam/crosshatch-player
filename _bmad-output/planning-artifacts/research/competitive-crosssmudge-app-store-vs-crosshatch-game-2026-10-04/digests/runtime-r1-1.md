### Lifecycle
- claim: Callbacks are global functions looked up by name: `on_init`, `on_update`, `on_draw`, `on_button(name, pressed)`, `on_touch(x, y, eventType)`, `on_tap(x, y)`, `on_swipe(dir)` and `on_exit`. - claim: The event model is a hybrid poll and redraw. In each `loop()` tick, every button *release* is dispatched as `on_button(name, true)`, so apps never see a press-down event. ## Leads worth chasing
- Whether `LuaAppActivity` dispatch can compile on a `CROSSSMUDGE_APP_CAP_TOUCH=0` build. It calls `mappedInput.wasScreenTapped`/`wasSwipe` unconditionally, and the touch gate forbids `MappedInputManager::wasScreen*`, so either those calls are inline stubs or the gate would fire. This affects D-security/D-device.
- Whether entering sleep destroys the activity, which would call `on_exit` and save state, or whether app state is lost on sleep. Trace `SleepActivity`/`ActivityManager` against `LuaAppActivity`.
- The security posture of the App Store (`AppStoreActivity.h`, 1068 lines). It downloads arbitrary Lua that has full SD access and `load`/binary chunks. Check for any signing or review gate.
- `l_findSection`'s callback streaming, LuaRunner.cpp:1169-1345, is a reusable pattern for streaming large data with no heap.
- Whether the task watchdog resets the device during a runaway Lua loop. This is untested; a fixture app would confirm it.
