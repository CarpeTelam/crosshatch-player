# Three first-party games ship with each release

## Description

Writes Sudoku, Ultimate tic-tac-toe, and Battleship as script packages that use only API level 1, which the fork release workflow of AD-25 packs and attaches to each release, and a PR-time check over `games/<id>/`. Their nearby rounds are epic-play-nearby's, and the API level 1 freeze and the starter repo epic-api-freeze's (owner, 2026-10-04).

## Outcome

Every release ships three games that a player installs and plays solo and in pass-and-play, hidden included; CAP-10's success check for those modes and CAP-1's "no game-specific firmware code" check are the signal (the nearby rounds close CAP-10 in epic-play-nearby).

## Requirements

This epic owns CAP-10 except the nearby rounds (epic-play-nearby; epic-script-runtime built the host API itself) and closes CAP-1's success check ("no game-specific firmware code"); epic-api-freeze closes CAP-1's versioned API by freezing level 1. Written at inception, 2026-10-04; lines without a CAP id cite their source.

- R1 (CAP-10; `first-party-games.md`; game-api-seed §1): three packages in `games/<id>/`, each with `api` 1: `sudoku` (`modes` `["solo"]`, `seats {1, 1}`, `hidden` false), `ultimate-tic-tac-toe` (`["pass"]`, `seats {2, 2}`, `hidden` false), and `battleship` (`["pass"]`, `seats {2, 2}`, `hidden` true). Manifests declare only `solo` or `pass`; epic-play-nearby adds `nearby` to the two-player games, so each two-player `draw` shows one seat's view and nothing but the manifest has to change. Each packs with `scripts/pack_game.py`. Each game's rounds, checks, and dev tools stay in its companion folder `test/game_script/first_party/<id>/`, and engine fixtures in `test/game_script/fixtures/` (R2); neither goes in `games/`.
- R2 (CAP-1 success; SPEC Constraints; owner Decision 2026-10-04, each game later leaves for its own repository): three parts stay apart. The engine (`src/`, `lib/`, `docs/crosshatch/api-level-1.txt`) gets no game-specific code: the epic changes nothing there, adds nothing to the API, needs no flash share, and leaves `API_SURFACE_CRC` alone. The repository's tooling (the test harness, CI, `scripts/`) names no game: the games check is generic, and engine tests use fixtures in `test/game_script/fixtures/`, never a game in `games/`. Each game is self-contained: `games/<id>/` is its whole package (rules, drawing, text, which is the game's own and not `tr()`, and data such as Sudoku's bank, all checked in), it shares no file or `require` with another game and names no repository path, and everything else it owns (its rounds, its own checks, its dev tools) sits in its companion folder `test/game_script/first_party/<id>/`, so `games/<id>/` and that folder are all that move when the game leaves.
- R3 (CAP-10; `first-party-games.md`, Shared board; R2): one 9×9 board module (the layout computed from `ch.screen.w` and `ch.screen.h`, about 50 px cells on the X4 Pro, a grid with heavier 3 × 3 block lines, cell rectangles, and the tap-to-cell mapping) is written in `ultimate-tic-tac-toe` and copied once into `sudoku`, since `require` loads only from a package's own root; from then on each game owns its copy, and nothing ties the two together.
- R4 (CAP-10; `first-party-games.md`, Sudoku; owner Decisions 2026-10-04, after crossplay's Sudoku+ and Sudoku): Sudoku plays as Sudoku+ does: tap a cell, then a digit on a 3 × 3 pad (no text entry); tapping the selected cell deselects it, and a write lets go of the cell. NOTES toggles pencil mode; a mark is a dot in its digit's pad position (1 top-left, 9 bottom-right), a grey ring (a `"dark"` filled circle with a white one inside it) or, for the focused digit, solid black, and a menu toggle draws marks as small digits instead: 18 package images of about 10 × 14 px, nine with the 50% dither baked into their 1-bit pixels for the grey marks and nine solid black for the focused digit, drawn in the same 3 × 3 slots (`ch.gfx.image` is opaque, so each carries its own white paper over SHADE PEERS's `"light"` fill, which Sudoku+ paints by hand); `ch.gfx.text` cannot draw grey (Sudoku+ greys its numerals by redrawing odd anti-diagonals white, about 9,500 line calls for a full grid, over `frame_commands_count`) and would need Ubuntu 10's ascender hardcoded, since there is no `ch.text_height`; marks a peer's digit rules out are hidden at draw time, never erased. The focused digit's copies on the board are drawn emphasised. ERASE clears the selected cell's digit and notes; UNDO steps back one cell at a time, and one FILL NOTES as a single step, through a bounded ring kept in `state`. A digit that clashes with a peer is marked, and clues cannot be changed (`apply` rejects it with a reason). A menu panel, a full-page sheet drawn in place of the board, holds HINT (selects the cell the solver of R5 can prove next and names its rule, never the digit, and first selects a digit that disagrees with the answer), FILL NOTES (every legal candidate into every empty cell), CHECK (strikes the player's digits that disagree with the answer, or says all correct), the toggles SHADE PEERS (the selected cell's row, column, and box drawn `"light"`), SHOW REMAINING (each pad key's count still to place), and notes as dots or digits, and HOW TO PLAY, a page drawn in place of the board with the rules, the controls, and the puzzle credit "Puzzles from the Sudoku Exchange puzzle bank (sudokuexchange.com), public domain."; the toggles are remembered per device in `ch.store`. HINT's and CHECK's marks last until the next edit. No clock is drawn while solving: each move carries the time since the previous one and `apply` adds it to the elapsed time in `state`; a full grid with no clash ends the round with `winners = {1}`, the end screen shows the elapsed time, and on `over` `input` records the best time per difficulty in `ch.store`, except for a solve that used HINT.
- R5 (CAP-10; `first-party-games.md`, Sudoku; owner Decisions 2026-10-04): puzzles come from a bank in the package's `puzzles.lua`, 81 characters each, taken from the public-domain Sudoku Exchange puzzle bank (`grantm/sudoku-exchange-puzzle-bank`, generated with QQWing and rated with Sukaku Explainer; its files `easy.txt`, `medium.txt`, and `hard.txt`, while `diabolical.txt` needs techniques the solver below lacks); `puzzles.lua` records the source repository's commit and each puzzle's 12-character hash. Each puzzle's band is the hardest technique the Lua solver below needs to finish it, crossplay's four bands: Easy (singles), Medium (locked candidates), Hard (pairs), and Expert (triples, X-wing, XY-wing, swordfish), so a label means what HINT's solver needs; a source puzzle the solver cannot finish is left out. Difficulty is a manifest `settings` entry with those four values, read from `ctx.settings`; `setup` picks a puzzle of that band at random and applies a random symmetry (digit relabelling, band, stack, row, and column swaps within their groups, transposition), so Play again deals a new grid, and `state` may hold the puzzle as its bank index and symmetry rather than its 81 characters. A Lua port of crossplay's technique ladder (`SudokuCore`), the cheapest technique first, finds HINT's next step and solves the puzzle for HINT's and CHECK's answer. The game's own checks (`checks.lua` in its companion folder, run by the games check) show every bank puzzle is a valid grid with exactly one solution, by a solution counter that shares no code with the solver, and that the solver finishes it at the band it is filed under; the tool that builds the bank is the game's, in its companion folder's `tools/`, not a fork script in `scripts/`. On-device generation is not in v1 (measured at inception, 2026-10-04: one attempt of crossplay's carve costs about 3.1 M Lua instructions at Easy and 8.1 M at Hard, over the 2 M budget, while one solve costs at most about 0.25 M).
- R6 (CAP-10; `first-party-games.md`, Ultimate tic-tac-toe): standard rules: seat 1 plays x, seat 2 circle; the cell played sends the next player to the matching small board, and to any open small board when that one is won or full; three won small boards in a line win; a big board with no line left to make is a draw. The whole board is drawn with the module of R3, the small boards the player may play in are highlighted, the player taps a cell directly, and there is no zoomed view. A `question` icon button opens a HOW TO PLAY page in place of the board with the rules and the controls; a tap closes it.
- R7 (CAP-10, CAP-6 as built; `first-party-games.md`, Battleship; owner Decisions 2026-10-04): a 10 × 10 board and a fleet of five ships (5, 4, 3, 3, 2). Placement runs one seat at a time (`status` names one turn seat): ships may touch but not overlap; each ship placed is a move that keeps the turn, rotation is the seat's `ui`, a Random move places the remaining ships, a Clear move lifts every placed ship and keeps the turn, and Ready, once all five are placed, passes the turn, so the runtime's Result and hand-off hide the fleet; then the seats alternate one shot per turn, a repeated shot is rejected with a reason, the mover sees hit, miss, or sunk in Result, and the first seat to sink the whole fleet wins. While firing, the target board is drawn large (about 44 px cells) and the seat's own fleet small (about 28 px cells) below it; each `draw` shows only its seat's fleet and its own shots, and seat 0 at Over shows both fleets. A `question` icon button opens a HOW TO PLAY page in place of the boards with the rules, placement, and firing; a tap closes it, and it shows no board, so it reveals nothing in a hidden match.
- R8 (CAP-8 as built; Done when 3 as amended 2026-10-04): marks and controls come from `GameIcons`, such as `x`, `circle`, and `question` (Ultimate tic-tac-toe), `fire`, `dot-outline` or `waves`, `boat`, `arrow-clockwise`, `shuffle`, `check`, and `question` (Battleship), and `pencil-simple`, `eraser`, `arrow-u-up-left`, `lightbulb`, and `check` (Sudoku); boards, Sudoku's digits and dot notes, and Battleship's small fleet board are drawn with `ch.gfx` shapes and text; every icon a game names is in `api-level-1.txt`'s `icon` entries. Sudoku ships its note digits as package images (R4); any game may also ship `icon.png`, `title.png`, or `handoff.png`.
- R9 (CAP-10; SPEC Constraints; `first-party-games.md`, Common rules; owner Decision 2026-10-04): every snapshot of every game, as the runtime encodes it, stays within 700 B, half of `state_bytes` (1,400), at every step of every round the games check plays; boards are packed strings (the inception shapes: Ultimate tic-tac-toe about 110 B, Sudoku about 550 to 620 B with the puzzle as bank index and symmetry, values, notes as a 9-bit mask per cell, the undo ring with one notes copy for FILL NOTES, the elapsed time, and a hint flag, Battleship about 260 B); a builder may choose any shape within the ceiling. Moves stay within `move_bytes`, and no call faults at the 2 M-instruction budget or the frame limits.
- R10 (CAP-10; Done when 5; R2; owner Decisions 2026-10-04): the games check is a harness target under `test/game_script/` that names no game. It finds every `games/<id>/` at configure time (the root a CMake cache variable, so scratch trees stay in the build directory), packs each with `pack_game.py` at build time, installs it with the real installer, runs the game's own checks from its companion folder's `checks.lua` when it has one, and plays every round in its companion folder's `rounds/` in each declared mode it can play on the host, `solo` and `pass`, logging each other declared mode it skips (epic-play-nearby's device rounds cover `nearby`), each round carrying its `settings` and a seed for the game's random source, drawing every local seat after each step; it fails on a pack or load failure, any fault, a snapshot over R9's ceiling, an outcome other than the round's file states, a failing game check, a game with no rounds, or a companion folder with no game. `test/game_script/first_party/README.md` documents the companion folder (the rounds format and the `checks.lua` interface). It runs in upstream's `unit-tests` job, which builds every target, and in the fork job `games-check` in `crosshatch-ci.yml`, which builds and runs only this target and is listed in `Crosshatch Test Status`'s `needs`, so the gate does not depend on upstream's workflow; the job's commands are run once from a fresh clone before the entry counts as built (AGENTS.md). It changes no upstream file (`test/CMakeLists.txt`, ledger row 3, already adds `game_script`). Epic-play-nearby's nearby changes must pass it.
- R11 (CAP-7, CAP-6 as built; `deferred-work.md` `## e5-close`, V3; R2): each game survives sleep and Continue through the solo and pass resume epic-pass-and-play built, checked on the device (R12). The engine's pass resume gets harness `PassResumeTest` cases over a fixture with a move that keeps the turn: a hidden pass match saved in Paused, and one whose snapshot was written mid-turn in Playing, each resuming into the hand-off with that move's change kept.
- R12 (CAP-10 success, Done when 2; `deferred-work.md` `## e5-close` (5.13), `## e6pre-13`, `## e5-r5`, `## e5-r2`, `## owner-e4-games-cap`; epic-api-freeze Notes, the Lua C-stack item): on an X4 Pro the owner installs the three packages through the inbox and plays each a round in every mode it declares from Home in at most 3 taps, sleeps mid-round in each and continues (Battleship mid-placement too), checks 5.13's tap targets and a sleep from Over after a seat's move during Battleship, counts the `dropped a touch before the frame was on the panel` lines after "I'm ready", runs B7.6 with the `pass-store.chgame` that `scripts/pack_device_run.py` writes into the packet, and records each game's "VM stopped" line (arena peak and stack high-water) and the launcher's free heap with the three games installed, and times Sudoku's HINT and CHECK on the bank's hardest Expert puzzle against the 3 s watchdog (the runtime-performance research, B3: below about 670,000 Lua instructions a second, a call near the 2 M budget meets the watchdog first); `owner-e4-games-cap`'s investigation stays deferred (its trigger is a games epic after epic-play-nearby, and three games are far from the 64-game cap), with the heap figure added to its entry.
